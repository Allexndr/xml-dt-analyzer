# XML-анализатор деклараций на товары: реализуемость, архитектура, флоу, риски

Основание: ТЗ v1.0 от 04.11.2026. Документ дополняет и исправляет предыдущий план.

---

## 0. Коротко

**Продукт реализуем.** Но это не «чат с ИИ над XML», а три слоя, и ИИ среди них самый тонкий:

1. **Детерминированное ядро.** Парсинг, индекс узлов с точными координатами, подсчёты, поиск, классификаторы, правила. Без ИИ работает и проверяется автотестами.
2. **Знания предметной области.** Карта «понятие → элемент XML → графа ДТ» для каждой версии схемы, классификаторы, правила проверки, нормативные пункты с редакциями. **Это главный объём работы.** Его делает связка разработчика и таможенного эксперта, а не код.
3. **ИИ как переводчик.** Понимает вопрос, выбирает инструменты, формулирует ответ. Числа, значения и номера строк в ответ подставляет сервер, а не модель.

**Почему, скорее всего, провалился предыдущий разработчик.** Задачу восприняли как программистскую («подключить LLM к XML»), а она наполовину про инженерию знаний. Без эталонных файлов, без словаря терминов («товар» — это что?) и без формализованных правил ответы невозможно ни сделать достоверными, ни сдать.

**Реалистичный срок MVP:** 16–20 недель для 2 разработчиков и таможенного эксперта на 0,3–0,5 ставки. Прошлую оценку в 11–13 недель я считаю оптимистичной: в ней не заложена инженерия знаний и админка нормативной базы. Срок действителен только после фазы 0 (раздел 10).

## 2. Главная развилка ТЗ

ТЗ одновременно требует:

- «ИИ не придумывает теги, строки, значения; считает точно» (п. 7.4, раздел 13);
- «пользователь задаёт вопросы в свободной форме» (п. 5).

Оба требования выполнимы одновременно, если **разделить вопросы на классы**:

| Класс | Пример | Кто отвечает | Гарантия |
|---|---|---|---|
| A. Факт из XML | «Кто отправитель?», «Сколько товаров?» | Инструменты ядра, ИИ только формулирует | Полная: каждое значение и строка из индекса |
| B. Структура формата | «Какой тег отвечает за графу 31?», «Может ли тег повторяться?» | Справочник схемы (XSD + карта граф) | Полная в пределах поддерживаемой версии |
| C. Проверка заполнения | «Правильно ли заполнена графа 44?» | Движок правил | Полная для реализованных правил. Для остальных честно пишем «правило не реализовано» |
| D. Нормативный вопрос | «Как заполняется графа 8 при ИМ 40?» | Поиск по пунктам + ИИ | Цитата и ссылка на пункт проверяются. Пересказ помечается как интерпретация |
| E. Свободная интерпретация | «Есть ли тут что-то подозрительное?» | ИИ над результатами инструментов | Без гарантии, с явной пометкой «интерпретация ИИ» |

Это прямо закрывает требование п. 5.6 различать факты, требования формата, правила и интерпретацию. В интерфейсе у каждого утверждения есть метка класса.

## 4. Ключевые архитектурные решения

### 4.1. Детерминированное ядро, ИИ — переводчик

ИИ никогда не видит XML целиком. Он видит:
- вопрос и сжатое состояние диалога;
- каталог понятий для версии схемы файла (4.2);
- результаты вызванных инструментов (JSON с идентификаторами доказательств).

Следствия: размер файла не влияет на контекст модели, расход токенов предсказуем, слабая локальная модель справляется, потому что задача у неё узкая.

### 4.2. Семантический слой: каталог понятий по версиям схемы

Модели нельзя давать писать XPath. Вместо этого:

- **Каталог понятий** для каждой версии схемы: `consignor` (отправитель), `consignee`, `declarant`, `customs_procedure`, `goods_item`, `hs_code`, `origin_country`, `invoice_value`, `marking_code`, `document_44` и т. д. Каждое понятие содержит:
  - путь (или несколько путей) в схеме этой версии;
  - уровень: декларация или товар;
  - графу ДТ;
  - множественность и обязательность из XSD;
  - синонимы на русском («отправитель», «грузоотправитель», «графа 2»).
- **Инструменты принимают id понятия**, а не путь. Неизвестное понятие возвращает ошибку, а не пустоту.
- **Для редких вопросов** есть ограниченный DSL запросов: фильтр по имени элемента, значению, товару. Имена элементов проверяются по XSD этой версии до выполнения. Произвольный XPath пользователю и модели недоступен (это ещё и защита от тяжёлых запросов).

Каталог понятий — главный актив продукта. Он делается полуавтоматически: генерация черновика из XSD и описания структуры из Решения № 75, затем ручная проверка экспертом. Новая версия схемы означает новый каталог, а не новый код.

### 4.3. Ответ с плейсхолдерами вместо проверки постфактум

Модель возвращает не свободный текст, а структуру:

```json
{
  "summary": "В декларации {{r1.count}} товарных позиций. Коды маркировки есть у {{r2.count}} из них.",
  "facts": [
    {"text": "Всего кодов маркировки: {{r3.count}}", "evidence": ["r3"], "kind": "xml_fact"},
    {"text": "Нет кодов у товаров {{r4.goods_list}}", "evidence": ["r4"], "kind": "xml_fact"}
  ],
  "interpretation": null
}
```

- Сервер подставляет значения из результатов инструментов `r1..rN`. Модель физически не может написать неверное число.
- Ссылки на строки строит интерфейс по `evidence`. Модель номера строк не пишет вообще.
- Верификатор остаётся вторым рубежом: в тексте вне плейсхолдеров не должно быть цифр, кодов и имён тегов, которых нет в результатах инструментов. При нарушении — одна перегенерация, затем ответ-шаблон без ИИ («Найдено: …») с пометкой.
- Для слабых моделей без надёжного JSON есть запасной путь: классификатор намерения + шаблонный ответ без генерации текста.

### 4.4. Координаты: смещения, а не строки

- Индексатор работает на **исходных байтах** файла потоковым парсером (expat через `defusedxml`). На событиях начала и конца элемента он получает байтовые позиции и сохраняет `byte_start`/`byte_end` всего элемента и отдельно его текстового значения.
- Байтовые смещения переводятся в символьные позиции в той же кодировке, в которой файл декодирован для показа. Для браузера — в позиции UTF-16, потому что так считает редактор.
- Номера строк вычисляются из смещений **по тем же правилам переноса строк, что у редактора** (`\r\n`, `\n`, `\r`). Это закрывается автотестом.
- Если файл однострочный (или строки длиннее порога), интерфейс предлагает режим «отформатированный вид». Он строится на лету с таблицей соответствия «смещение в оригинале → смещение в форматированном виде». Ссылки и подсветка работают в обоих режимах, оригинал не меняется. В ссылке явно указано, к какому виду относится номер строки.
- XSD-валидация идёт отдельным проходом через `lxml` с локальным каталогом схем. Ошибки валидации тоже привязываются к позициям.

### 4.5. Локальный ИИ: браузер как ретранслятор

Проблема: сервер в облаке не достанет до модели на `localhost` пользователя.

Решение: **один оркестратор на сервере, транспорт до модели меняется**.

```
API-режим:     сервер-оркестратор ──HTTPS──▶ провайдер ИИ
Локальный:     сервер-оркестратор ──WebSocket──▶ браузер ──HTTP──▶ localhost:11434 (Ollama / LM Studio / vLLM)
```

- В локальном режиме сервер отправляет запрос к модели в браузер по открытому WebSocket. Браузер передаёт его на локальный адрес, ответ возвращает серверу.
- Содержимое декларации к стороннему ИИ-провайдеру не уходит (п. 8.1 выполнен). Но файл всё равно лежит на нашем сервере. Если заказчик понимает «локально» как «вообще ничего не уходит с компьютера», нужна **отдельная поставка в Docker** для установки у клиента. Это нужно спросить на фазе 0.
- Технические условия, которые надо проверить в спайке:
  - для Ollama нужна настройка разрешённых источников (`OLLAMA_ORIGINS`), иначе браузер заблокирует запрос (CORS);
  - Chrome спрашивает разрешение на доступ к локальной сети у страниц из интернета; Safari и Firefox ведут себя иначе в части обращений с HTTPS-страницы к `http://localhost`;
  - в интерфейсе нужен мастер подключения: проверить доступность, получить список моделей, сделать тестовый вызов с инструментами.
- Поддерживаемые API: Ollama и OpenAI-совместимый (его поддерживают LM Studio, vLLM, llama.cpp-server). Этого достаточно для MVP.

### 4.6. Правила проверки как код с юридической привязкой

Каждое правило:

```yaml
id: G44-001
title: Наличие инвойса в графе 44 при ИМ 40
applies_if: "procedure in ['40'] "
check: "exists(document_44 where kind in classifier('doc_kinds','invoice'))"
legal_ref: {doc: "257", edition: "ред. от …", provision: "п. …"}
valid_from: …
valid_to: …
severity: error
needs_data_if: "…"
tests: [fixtures/G44-001/*.xml]
```

- **Пять статусов результата:** `violation` (нарушение подтверждено), `needs_info` (данных недостаточно), `pass`, `not_applicable` (условие не наступило), `not_implemented`. Это закрывает требования п. 5.4 и 5.5 о том, что «отсутствие ≠ ошибка».
- Пользователь всегда видит **покрытие**: «Проверено 18 правил из базы. Полная проверка ДТ не выполнялась». Это требование раздела 12 ТЗ о разграничении автоматических проверок и ответов ИИ.
- **Дата, на которую проверяем,** — отдельный параметр. По умолчанию берётся дата из ДТ, если она есть, иначе текущая. Пользователь может её поменять. От неё зависят выбранные редакции норм и классификаторов.
- Простые правила описываются декларативно, сложные пишутся функцией на Python. И те, и другие имеют фикстуры и прогоняются в CI.

### 4.7. Нормативная база: пункт как единица хранения

- Документы хранятся в модели `document → edition (valid_from, valid_to, источник, хэш текста) → provision (номер пункта, путь в структуре документа, текст)`.
- Поиск **гибридный**: полнотекстовый поиск PostgreSQL с русской морфологией, точное совпадение номеров граф и пунктов, векторный поиск как дополнение. Результаты объединяются и переранжируются.
- Ответ на нормативный вопрос обязан содержать цитату. Верификатор проверяет, что пункт существует в выбранной редакции и цитата является его подстрокой.
- Если подходящих пунктов нет, ответ звучит так: «В подключённой базе нет сведений по этому вопросу». Пересказ без цитаты не выдаётся.

           │ REST                         │ SSE (стрим ответа)            │ WebSocket

│  Загрузка → проверка → определение версии → XSD → индексатор (фоновая задача)          │

| Слой | Выбор | Почему |
|---|---|---|
| Просмотрщик XML | **CodeMirror 6** | Рендерит только видимую часть, держит большие документы лучше Monaco, проще декорации и фолдинг. Monaco допустим, но на файлах десятков МБ тяжелее |
| Бэкенд | Python 3.12, FastAPI | Лучшие инструменты для XML: `lxml` (XSD), `expat`/`defusedxml` (позиции, безопасность) |
| Фоновые задачи | Встроенные задачи FastAPI на старте, затем очередь (RQ/Celery/Arq) | Индексация больших файлов не должна блокировать запрос |
| БД | PostgreSQL 16, pgvector | Индекс узлов, история, нормативка, полнотекстовый поиск — в одной базе |
| Файлы | S3-совместимое хранилище (MinIO у себя или облако в нужной юрисдикции) | Оригинал хранится байт в байт, SHA-256 |
| Вход | Одноразовый код или magic link на e-mail | Без паролей. Нужен SMTP-провайдер с SPF/DKIM, иначе письма уходят в спам |
| Наблюдаемость | Логи без содержимого файлов и вопросов, метрики латентности, трассировка вызовов инструментов | Отладка без утечки данных |

## 6. Модель данных (основное)

```
users(id, email, created_at)
sessions(id, user_id NULL, anon_token_hash, expires_at)
files(id, owner_session_id | owner_user_id, name, size, sha256, encoding, storage_key,
      doc_type, schema_version, status, created_at, expires_at)
file_validation(file_id, is_wellformed, xsd_valid, errors jsonb)
nodes(file_id, node_id, parent_id, depth, ns, local_name, path, value_text,
      byte_start, byte_end, val_start, val_end, line_start, line_end, goods_no, concept_id NULL)
  — индексы: (file_id, local_name), (file_id, concept_id), (file_id, goods_no)
conversations(id, file_id) — строго один файл
messages(id, conversation_id, role, question, answer jsonb, created_at,
         model, provider, prompt_version, kb_snapshot_id, check_date)
tool_calls(message_id, seq, tool, args jsonb, result jsonb)
evidence(message_id, evidence_id, node_id, kind, label)
dialog_state(conversation_id, named_sets jsonb)   — «последние товары», «товары с маркировкой» …

schema_versions(id, code 'R.055', version '1.2.0', namespace, valid_from, xsd_bundle_key)
concepts(id, schema_version_id, key, paths[], level, graph_no, min_occurs, max_occurs, synonyms[])
classifiers(id, code, name, source_doc, edition_id) / classifier_items(classifier_id, code, name, valid_from, valid_to)
documents / editions / provisions(+ tsvector, embedding)
rules(id, version, definition, legal_ref → provision_id, valid_from, valid_to, status)
kb_snapshots(id, created_at, manifest jsonb)   — фиксирует версии всего для воспроизводимости
ai_settings(owner, mode, provider, base_url, model, api_key_encrypted NULL)
```

**Воспроизводимость:** каждое сообщение ссылается на `kb_snapshot_id`, хранит вызовы инструментов и их результаты. Поэтому ответ из истории открывается ровно в том виде, в каком был дан. Отсюда же поле «использованная редакция документа», которое требует п. 4 ТЗ.

**Изоляция файлов:** беседа принадлежит одному файлу, все запросы инструментов фильтруются по `file_id` на уровне сервиса. Строковые политики безопасности PostgreSQL (RLS) — дополнительный рубеж.

## 7. Флоу

### 7.1. Загрузка файла

```
Выбор/перетаскивание
 → Лимит размера (на клиенте и на сервере) → потоковая загрузка в хранилище, SHA-256
 → Определение формата: XML или архив/конверт? (ZIP: распаковать с лимитами и показать список файлов)
 → Определение кодировки: BOM, XML-декларация, иначе UTF-8 с проверкой
 → Проверка корректности (безопасный парсер: без DTD, без внешних сущностей, лимиты глубины)
     ошибка → понятное сообщение: «Файл не является корректным XML: строка 120, позиция 15,
              не закрыт тег <…>» + подсветка места
 → Определение типа и версии по пространству имён корня
     неизвестная версия → файл открывается в режиме «просмотр и поиск», ИИ отвечает только
              на общие вопросы, пользователь предупреждён
 → XSD-валидация (ошибки сохраняются с позициями; невалидный файл всё равно открывается)
 → Индексация (фоновая задача, прогресс-бар; для маленьких файлов синхронно)
 → Привязка узлов к понятиям каталога, вычисление номера товара для каждого узла
 → Статус «готов» → страница анализа
```

Ключевое: **невалидный по XSD файл открывается и анализируется**. Пользователь как раз и хочет понять, что в нём не так.

### 7.2. Вопрос → ответ

```
1. Вопрос + id беседы
2. Роутер классов (2): быстрые правила + классификация моделью
3. Разрешение ссылок на контекст: «из них», «у этих» → named_sets из dialog_state
4. План вызовов инструментов (модель) → проверка аргументов (понятия существуют в этой версии)
5. Выполнение инструментов → результаты r1..rN с evidence
6. Генерация ответа с плейсхолдерами (4.3)
7. Подстановка значений, верификация; при сбое — перегенерация или шаблонный ответ
8. Сохранение: сообщение, вызовы, evidence, модель, снимок базы знаний, дата проверки
9. Стрим ответа в интерфейс (SSE): сначала статусы «ищу товары…», затем текст, затем ссылки
```

Статусы шага 9 закрывают требование ТЗ «отображение состояния обработки вопроса».

### 7.3. Продолжение диалога

Пример из ТЗ: «Сколько товаров?» → «5». «А у каких из них есть маркировка?»

- После первого ответа в `dialog_state` сохраняется именованный набор `last_goods = [1..5]`.
- Во втором вопросе роутер видит «из них» и передаёт инструменту `filter_set(last_goods, has=marking_code)`.
- История в промпт попадает только как краткая структурированная сводка. Это не даёт данным разных файлов смешаться и экономит контекст.

### 7.4. Клик по ссылке

`evidence → node_id → (start, end) в текущем режиме показа → прокрутка + подсветка диапазона`. Подсветка предыдущей ссылки снимается. Свёрнутые блоки, содержащие цель, автоматически разворачиваются. Если ссылок много (например, 125 кодов маркировки), они группируются по товарам с раскрытием.

### 7.5. Проверка заполнения

```
Пользователь просит проверку (или кнопка «Проверить по правилам»)
 → дата проверки (из ДТ / текущая / выбранная) → снимок норм и классификаторов на эту дату
 → отбор применимых правил по условиям (процедура, вид товара …)
 → прогон → результаты по 5 статусам
 → ИИ формулирует объяснение только по результатам; ссылки на пункты — из legal_ref правил
 → в ответе: покрытие («проверено N правил из M»), что не проверялось
```

### 7.6. Нормативный вопрос

`гибридный поиск пунктов в редакции на дату → топ-K → ответ с обязательными цитатами → верификация цитат → метки «правило заполнения» / «интерпретация ИИ»`.

### 7.7. Настройка ИИ

Мастер: выбор режима → адрес и модель → «Проверить подключение» (доступность, список моделей, тестовый вызов с инструментами) → предупреждение о передаче данных (для API) с явным согласием → сохранение. Переключение режима не трогает файл и историю. Каждое сообщение помнит свою модель.

### 7.8. Анонимная сессия и вход

- Анонимный пользователь получает httpOnly-cookie с токеном сессии. Срок хранения (например, 7 дней) показан у каждого файла: «Будет удалён 13.11.2026».
- При входе по e-mail интерфейс спрашивает: «Перенести 3 файла из этой сессии в аккаунт?». Перенос меняет владельца, а не копирует данные.
- Ограничения на анонимов: число файлов, размер, частота вопросов к серверному ИИ.

### 7.9. Обновление базы знаний (админка)

```
Новая редакция документа → загрузка текста → разбиение на пункты (полуавтоматически) →
 проверка экспертом → публикация с valid_from →
 diff с прошлой редакцией: какие правила ссылаются на изменённые пункты →
 эти правила помечаются «требует пересмотра»
```

Аналогично для новой версии XSD: загрузка пакета схем → генерация черновика каталога понятий → разница с прошлой версией → проверка экспертом → публикация.

Без этого п. 7.3 ТЗ («обновление без переработки системы») не выполнить. Это 1,5–2 недели работы, которых нет в ТЗ явно.

### 7.10. Удаление

Удаление файла: оригинал из хранилища, индекс узлов, беседы, вызовы, эмбеддинги (если были), кэш. Пользователь выбирает, удалять ли историю (п. 10 ТЗ). Отдельно в политике конфиденциальности нужно указать срок хранения в резервных копиях: из них данные мгновенно не удаляются.

## 8. Подводные камни

Формат: что может пойти не так → почему это легко не заметить → что делать.

### 8.1. Предметная область

1. **Реальные файлы не R.055.** ТЗ опирается на Решение № 75, но пользователи могут приносить XML из национальных систем декларирования, из программ-декларантов, в конвертах с подписью. → Первым делом получить 10–20 реальных файлов от целевых пользователей. Архитектура закладывает несколько форматов через каталог понятий, но MVP поддерживает только то, что подтверждено образцами.
2. **«Товар» — неоднозначное слово.** Товарная позиция ДТ, наименование внутри графы 31, физическая единица, код маркировки — это четыре разные величины. → Глоссарий терминов, согласованный с заказчиком и зашитый в каталог понятий. Ответ на «сколько товаров» всегда уточняет, что именно посчитано.
3. **Маркировка.** Коды бывают индивидуальными и групповыми (агрегирующими). Служебный символ-разделитель GS недопустим в XML 1.0, поэтому в файле код может быть записан с заменой или без него. «Криптохвост» кода может отличаться при одинаковом идентификаторе товара. → Нормализация кодов перед поиском дублей (правило нормализации согласовать с экспертом). Отдельные метрики: кодов, уникальных кодов, групповых кодов, товаров с кодами.
4. **Условная обязательность.** Элемент необязателен в XSD, но обязателен при конкретной процедуре или виде товара. → Только через правила с условиями и статусом `needs_info`. Никогда не выводить нарушение из одного XSD.
5. **Карта «графа ↔ элемент» не один к одному.** Одна графа может собираться из нескольких элементов, один элемент может относиться к нескольким графам. Отдельные графы имеют подразделы. → Каталог понятий хранит связь «многие ко многим».
6. **Корректировка ДТ (КДТ) и другие виды документов** могут прийти вместо ДТ. → Определять тип по корню и честно говорить «этот тип документа не поддерживается в текущей версии».

### 8.2. XML и техника

7. **Однострочный XML** — см. 4.4. Без режима форматированного вида требование о ссылках на строки формально выполнено, по сути нет.
8. **Кодировки и BOM.** Windows-1251, UTF-8 с BOM, расхождение объявленной и фактической кодировки. → Детектор кодировки, байтовые позиции как источник истины, автотест «один и тот же документ в UTF-8, UTF-8+BOM, CP1251, CRLF, однострочном виде даёт одинаковые подсчёты и корректные ссылки».
9. **Пространства имён.** Префиксы в разных файлах могут отличаться при одинаковом пространстве имён. → Сопоставление только по паре (пространство имён, локальное имя). Поиск в интерфейсе по локальному имени.
10. **Связанные схемы XSD.** Схема R.055 импортирует схемы общей модели данных ЕАЭС с конкретными версиями. → Хранить полный пакет схем на каждую версию, разрешать импорты через локальный каталог, сеть при валидации запрещена.
11. **Большие файлы.** Тысячи кодов маркировки дают сотни тысяч узлов. → Потоковая индексация, пакетная вставка через COPY, виртуализация в редакторе, лимиты (например, 100 МБ), измерение на реальных файлах в спайке.
12. **Конверты и подписи.** Файл может содержать подпись XMLDSig или вложенный документ в base64. → Распознавать такие конверты. Вложенный документ показывать отдельной вкладкой с собственной нумерацией строк и честной пометкой. Исходный файл не менять.
13. **Позиции в разных системах счёта.** Байты (сервер), символы (Python), UTF-16 (браузер). → Одна функция преобразования с тестами, включая символы вне базовой плоскости Unicode.

### 8.3. ИИ

14. **Слабые локальные модели** не умеют надёжно вызывать инструменты и отдавать JSON. → Классы вопросов A и B работают и без модели (шаблоны). Публикуется список проверенных моделей с результатами прогона тестового набора. Остальные модели работают в режиме «без гарантий».
15. **Внедрение инструкций через данные.** Наименование товара в XML может содержать текст вида «игнорируй правила». → Данные передаются модели только как значения в JSON, у модели нет инструментов с побочными эффектами, числа подставляет сервер (4.3). Худший исход — странная формулировка, а не ложный факт.
16. **Дрейф качества** при смене модели или промпта. → Набор из 150–300 вопросов с ожидаемыми вызовами инструментов и ответами, прогон в CI на каждое изменение промпта и для каждой модели из списка.
17. **Стоимость.** → Ключ пользователя, кэш по (хэш файла, нормализованный вопрос, модель, снимок базы знаний), лимиты частоты, маленькая модель для роутинга.

### 8.4. Нормативная база

18. **Консолидированные редакции.** Решения № 257, 75 и 378 много раз изменялись. Для проверки исторических ДТ нужен текст **на дату**, а не только последний. → Хранить редакции с датами действия. Получение исторических редакций с adilet.zan.kz проверить в фазе 0.
19. **ТН ВЭД вне Решения № 378.** → Отдельный справочник ТН ВЭД ЕАЭС с версиями. В MVP можно ограничиться проверкой формата и существования кода, без проверки правильности классификации (последнее вообще не задача автомата).
20. **Национальные особенности РК.** ТЗ упоминает акты Республики Казахстан. → Юрисдикция MVP фиксируется явно. Национальные правила — отдельный набор с пометкой страны.
21. **Ответственность.** Пользователь может принять ответ за юридическое заключение. → Дисклеймер, метки «интерпретация ИИ», обязательные цитаты. В пользовательском соглашении — ограничение ответственности.

### 8.5. Безопасность

22. **XXE и «бомбы» сущностей.** → Запрет DTD и внешних сущностей, лимиты глубины, числа узлов, размера распакованного архива.
23. **SSRF через «адрес API».** → В серверном режиме: только HTTPS, запрет приватных и служебных адресов после разрешения DNS, запрет редиректов на них, отдельный исходящий прокси. Локальные адреса допустимы только через ретранслятор в браузере.
24. **API-ключи.** → Шифрование на сервере (AES-GCM, ключ из KMS или секрета окружения), ключ никогда не возвращается во фронтенд (показываются последние 4 символа), не пишется в логи. Для анонимов ключ живёт только в памяти сессии.
25. **Изоляция пользователей.** Классическая ошибка — доступ к чужому файлу по id. → Проверка владельца в каждом запросе, непредсказуемые идентификаторы, автотесты на доступ к чужим ресурсам.
26. **Anon-злоупотребления.** → Лимиты на IP и сессию, капча при подозрительной активности, лимит места.

### 8.6. Право и данные

27. **Локализация персональных данных.** В ДТ есть сведения о лицах. Законы о персональных данных РК и РФ требуют хранения на территории страны. → Выбрать юрисдикцию до выбора хостинга.
28. **Трансграничная передача во внешний ИИ.** → Явное согласие при включении API-режима, текст предупреждения согласовать с юристом заказчика. Только нужные фрагменты, а не файл целиком (это у нас и так по архитектуре).
29. **Коммерческая тайна.** → Шифрование хранилища, минимальный срок хранения, журнал доступа администраторов.

### 8.7. Проект и договор

30. **Неизмеримая приёмка.** «Достоверный ответ» без эталонов можно оспорить бесконечно. → В договор: каталог поддерживаемых вопросов, эталонные файлы, пороги метрик (раздел 9).
31. **Расползание объёма.** «Полная проверка ДТ» и «обучение ИИ». → Зафиксировать: «обучение» — это база знаний и правила, а не дообучение модели. Число правил MVP — фиксированный список.
32. **Эксперт как узкое место.** Без таможенника каталог понятий и правила не проверить. → Его время планируется с первого дня, с еженедельными сессиями разметки.
33. **Срок действия схемы.** R.055 v1.2.0 действует с 01.10.2026, следующая версия выйдет. → Поддержка нескольких версий заложена в модель данных с первого дня.

## 9. Тестирование и измеримая приёмка

**Эталонный набор**
- 10–20 реальных XML (обезличенных при необходимости) и ожидаемые значения: число позиций, наименований, кодов маркировки и уникальных кодов, документы по графе 44, ключевые реквизиты.
- Для каждого файла — его варианты: однострочный, CRLF, CP1251, с BOM. Результаты должны совпасть.

**Автотесты ядра**
- Каждое `evidence` указывает на диапазон, текст которого содержит ожидаемый тег и значение.
- Подсчёты совпадают с эталоном на 100%.
- Каждое правило имеет положительную и отрицательную фикстуру и фикстуру для `needs_info`.

**Набор вопросов**
- 150–300 вопросов по классам A–E с ожидаемыми вызовами инструментов и фактами.
- Метрики: точность фактов класса A — 100%; доля ответов с несуществующим тегом, строкой, пунктом — 0%; корректная маршрутизация по классам ≥ 95%; для класса D — все цитаты существуют в выбранной редакции.

**Производительность**
- Файл заданного размера (согласовать, например 50 МБ) индексируется за N секунд, интерфейс не зависает, прокрутка плавная.
- p95 «вопрос → первый токен» ≤ 3 с, «вопрос → полный ответ» ≤ 10 с на внешнем API.

**Безопасность**
- XXE, бомбы сущностей, ZIP-бомбы, SSRF, доступ к чужим ресурсам — автотесты.

| Этап | Недели | Результат | Демонстрация |

| 2. Просмотрщик: CodeMirror, фолдинг, поиск, подсветка, форматированный вид, панели | 2 (параллельно с 1) | Работа с XML без ИИ | **Релиз A** |

**Итого:** около 16–20 календарных недель после фазы 0 с учётом параллельной работы и буфера 15%.

**Почему релизы A и B важны:** заказчик видит рабочий продукт на 5–6-й неделе. Ранняя обратная связь по реальным файлам дешевле, чем переделка в конце.

### Что сознательно не входит в MVP

- Полная проверка всех правил заполнения ДТ (только согласованный список).
- Проверка правильности классификации по ТН ВЭД.
- Дообучение моделей.
- Форматы, кроме подтверждённых образцами.
- Мобильная вёрстка страницы анализа (главная страница адаптивна).
